# 코드 아키텍처

레이어드 + 도메인별 패키징.
의존 방향은 한 방향만: router → service → (repository | clients | agent) → domain

## 디렉토리 구조

```
app/
  main.py            # FastAPI 앱 조립 — traceId 미들웨어, 예외 핸들러, 라우터 등록, lifespan(스토어 선로딩), /health
  deps.py            # 의존성 주입 (Bearer JWT 검증 → user_id, traceId)
  core/              # 도메인 무관 공통 계층
    config.py        #   환경변수 설정
    auth.py          #   JWT 검증 (JWKS, RS256)
    dynamo.py        #   DynamoDB 커넥션, 타입 변환 (to_plain, to_storable)
    orm.py           #   SQLAlchemy 선언 베이스(BackendBase) — 패키지별 엔티티가 공유하는 메타데이터
    llm.py           #   Bedrock LLM 클라이언트
    clock.py         #   UTC 시각 유틸 (Z 접미 문자열 조립)
    ratelimit.py     #   유저별 토큰버킷 (인스턴스 로컬)
    errors.py        #   도메인 예외
    handlers.py      #   전역 예외 핸들러 — 예외를 {traceId, error} 실패 응답으로 번역
    logging.py       #   로깅 설정, traceId 필터
    schemas.py       #   공통 응답 스키마 (ApiResponse, CamelModel, ItemsData, ListData)
  clients/           # 외부 시스템 어댑터 — mysql.py(백엔드 MySQL 읽기 전용 실행기 + 경계 표기 변환)
  chat/              # 채팅 도메인: 스레드 CRUD, 메시지 전송(SSE), 요약(스레드 압축 + 유저 장기)
  users/             # 유저 도메인: 프로필·기피부위·체중 이력 — MySQL 직조회 (엔티티 UserProfile 등)
  workouts/          # 기록 도메인: 세션·종목·세트 조회 — MySQL 직조회 (엔티티 Workout 계열)
  routines/          # 루틴 도메인: 상세 API, 룰 필터 검색 + 임베딩 랭킹 + LLM 선택, 인메모리 스토어
  exercises/         # 운동 도메인: 종목 카탈로그 캐시, 종목 마스터 직조회(엔티티 Exercise 계열), 가이드 영상 URL
  charts/            # 차트 도메인: metric별 기록 조회(service)와 버킷팅, 집계 순수함수(domain)
  agent/             # LangGraph 챗봇: graph(툴콜 루프), guardrails, prompts, tools/
    tools/           #   chart, routine, exercise(§7 payload 스킴과 1:1), history(NL2SQL 기록 조회, text 응답). failures는 툴 실패를 LLM 안내 지시로 번역
scripts/             # 배치: 캐글 루틴 변환, DynamoDB 적재, 임베딩 계산, 종목 카탈로그 동기화, 로컬 개발 실행
tests/
data/                # 종목 metadata 정본(206종, 한글 확장), 캐글 별칭 매핑
demo-web/            # 데모용 웹 클라이언트 (Vite)
alloy/               # Grafana Alloy 사이드카 설정 (메트릭 수집)
docs/
```

도메인 패키지는 router, schemas, service, domain, repository 조합이며 필요한 것만 둔다. charts는 라우터 없이 agent 툴에서만 쓰이고, exercises는 domain이 없다.

## 패키지별 구성 — 저장소·연결·엔티티

패키지마다 붙는 저장소와 연결 방식, 엔티티(레코드) 보유 여부가 다르다. 연결 자원은 전부 lru_cache 싱글턴이라 프로세스당 1개를 공유한다.

| 패키지 | 구성 파일 | 저장소·연결 | 엔티티/레코드 |
|---|---|---|---|
| `chat` | router, schemas, service, domain, repository | DynamoDB 3테이블 (chat_threads, chat_messages, user_summaries) — core/dynamo의 공유 boto3 리소스(커넥션 풀·타임아웃 한곳) | `ThreadRecord` (domain, pydantic — 조립·만료 판정·to_item/from_item 소유). 메시지는 dict |
| `users` | domain, repository | 백엔드 MySQL 직조회 (clients/mysql 공유 엔진) — 프로필·기피부위·체중 이력, 구 내부 API §4.1·§4.4 형태 승계 | `UserProfile`, `UserAvoidedMuscle`, `BodyWeightLog` (domain, SQLAlchemy) |
| `workouts` | domain, repository | 백엔드 MySQL 직조회 — 기록 raw·종목별 세트·세션 요약, 구 §4.2·§4.5·§4.6 형태 승계 (0→null 변환 포함) | `Workout`, `WorkoutExercise`, `WorkoutSet` (domain, SQLAlchemy) |
| `routines` | router, schemas, service, domain, repository, prompts | DynamoDB routines — 부팅 Scan으로 인메모리 RoutineStore 라이트 로드(필터 필드+임베딩, ~350MB), 최종 선택 1건만 GetItem. 프로필·기록은 users·workouts repository 사용 | 없음(의도적) — 수만 건 상주라 pydantic 인스턴스화 비용이 커서 라이트 dict + numpy 유지 |
| `exercises` | router, schemas, service, domain, repository | DynamoDB exercise_catalog(일 1회 배치 캐시, URL 유일 출처) + repo 동봉 metadata JSON + MySQL 종목 마스터 직조회(구 §4.3) | `Exercise`, `Equipment`, `Muscle`, `ExerciseMuscle` (domain, SQLAlchemy) |
| `charts` | service, domain | 저장소 없음 — users·workouts repository로 조회 후 domain 순수 함수가 집계 | 없음 |
| `agent` | graph, guardrails, prompts, tools/ | Bedrock(core/llm), 기록 조회 툴은 workouts·exercises 엔티티 + clients/mysql | `AgentResult`(VO), `GraphEvent`(이벤트 어휘) |
| `clients` | mysql | SQLAlchemy 엔진 싱글턴(커넥션 풀, pool_pre_ping + recycle 3600s로 RDS wait_timeout 대응, 세션 READ ONLY, DB 장애→DomainError 번역, UUID·enum·시각 표기 변환) | 없음 — 엔티티는 각 도메인 패키지 domain.py 소속 |
| `core` | config, auth, dynamo, orm, llm, clock, ratelimit, errors, handlers, logging, schemas, sse | dynamo: boto3 리소스 싱글턴(테이블 핸들 공유) / llm: Bedrock 클라이언트 싱글턴 / orm: 엔티티 공유 베이스(BackendBase) | 공통 응답 스키마(CamelModel, ApiResponse 계열) — 와이어 계약이지 엔티티 아님 |

## 계층 규칙

| 파일 | 역할 | 금지 사항 | 스프링 대응 |
| --- | --- | --- | --- |
| `router.py` | HTTP 입출력만. 도메인 예외는 전역 핸들러가 HTTP로 번역 | 비즈니스 로직, DB 접근 | `@RestController` |
| `schemas.py` | pydantic 요청/응답 모델. `CamelModel` 상속(내부 snake_case ↔ 와이어 camelCase), 성공 응답은 `ApiResponse[모델]`로 팀 규약 `{traceId, data}` 강제 | 로직, I/O | DTO (Request/Response) |
| `service.py` | 비즈니스 흐름. 언제 무엇을 읽고 쓸지 결정, 트랜잭션 경계 소유 | `HTTPException` 직접 raise (도메인 예외를 던진다) | `@Service` |
| `repository.py` | DB 명령이 사는 유일한 곳 | commit, 조합 판단 | `@Repository`, Spring Data 인터페이스 |
| `domain.py` | I/O 없는 순수 함수, 상수, 저장 레코드 (예: ThreadRecord, 만료 판정, TTL 계산) | I/O 전부 | 엔티티의 비즈니스 메서드, 도메인 서비스 |
| `clients/` | 소유하지 않은 시스템(스프링 API)의 얇은 어댑터. 테스트 모킹 지점 | 비즈니스 판단 | `FeignClient`, `WebClient` 어댑터 |
| `core/` | 도메인 무관 공통 인프라 | 도메인 지식 | global/config/common 패키지, `@ControllerAdvice`(handlers) |

스프링 개념 중 이 서버에 없는 것들의 행방.

1. 엔티티: 각 도메인 패키지의 `domain.py`가 소유한다. 우리 소유 저장소(DynamoDB)는 pydantic 레코드(예: chat의 `ThreadRecord` — 조립 규칙, 만료 판정, to_item/from_item 소유, 정본은 [`docs/document-structure.md`](document-structure.md)), 백엔드 MySQL은 SQLAlchemy 엔티티(users·workouts·exercises의 domain.py, 정본은 [`docs/백엔드 ERD.md`](백엔드%20ERD.md))다. 선언 베이스(BackendBase)만 core/orm이 공유한다 — 패키지 간 FK가 한 메타데이터에서 풀리게.
2. VO: 별도 계층이 없다. 값 묶음이 필요하면 pydantic 모델이나 dataclass(예: chat service의 `_Turn`)로 그때그때 표현한다.
3. MVC의 Model: 단일 파일이 아니라 service + domain + repository 전체에 해당한다.

목록 응답 하나만 예외 규칙이 있다 — 커서를 안 쓰는 목록은 `ListData` 대신 `ItemsData`(page 없음)를 쓴다. 채팅 API는 `page` 객체를 내보내지 않기로 확정(클라이언트 API 명세 §공통)이라 `ListData`의 기본값 `page`가 계약을 깬다.

유저 데이터 읽기는 백엔드 RDS MySQL 직접 조회가 표준이다 (2026-08-12 내부 API 파기 합의, 같은 날 이관 완료 — spring 클라이언트 삭제됨) — 반드시 `clients/mysql.py`(읽기 전용 계정, 세션 READ ONLY, 바인딩 파라미터) 경유. 쓰기는 어디에도 없다 — 데이터 변경은 클라이언트→백엔드 공개 API의 몫이다. 구 내부 API의 응답 형태·책임(0→null, enum camelCase 변환)은 users·workouts·exercises repository가 승계했다.

## 의존성 주입 경계

두 스타일이 공존하며 기준은 수명이다. 요청마다 달라지는 값만 Depends로 주입하고, 프로세스 수명 자원까지 Depends로 내리면 라우터가 하위 계층의 자원을 전부 알아야 해 계층 규칙과 충돌하므로 싱글턴으로 둔다.

| 자원 | 방식 | 테스트 교체 |
| --- | --- | --- |
| 요청 문맥 (인증 user_id, traceId) | FastAPI Depends (deps.py) | `app.dependency_overrides` |
| 프로세스 수명 자원 (설정, DynamoDB 테이블, LLM 클라이언트, 루틴 스토어, 레이트리미터) | 모듈 함수 + lru_cache 싱글턴 (get_*) | monkeypatch (+ `cache_clear`) |

## 데이터 규칙 (요약)

- payload에는 식별자만 저장(slug, exerciseId) — URL과 미디어는 클라가 조회 시점에 획득
- 시각은 Z 접미 ISO 문자열(`2026-07-23T09:12:00Z`, core/clock.py) — pydantic의 datetime 직렬화(+00:00)가 팀 규약 표기와 어긋나 DTO에서도 str로 다룬다
- 식별자는 ULID(thread_id, message_id) — 생성 시각이 내장돼 SK 정렬 기준을 겸한다
- TTL은 `chat_threads.expires_at`에만 — 만료 시 스레드 항목만 삭제되므로 고아 메시지는 일 1회 배치 정리
- 요약 갱신은 응답 후 BackgroundTasks (n턴 도달 시, 스레드 압축과 유저 요약 증분 병합)
